# Autonomy — front-loaded, then run start-to-finish

Operating rule for any process that runs unattended (`aidex-plan-exec`,
`aidex-audit`, `aidex-loop`). Full canon:
`~/.claude/skills/aidex-conventions/references/autonomy-conventions.md`.

**Core principle:** once a process starts, run it autonomously **start to finish**.
All questions are asked in the **initial phase** (plan design / audit kickoff /
loop design interview). The run itself does not stop to ask permission or opinion.

During the run, classify before pausing:

1. **Deny — never, even mid-run, and never pre-authorizable:** destructive ops on **real** data (dropping/resetting/truncating an app database in any environment), destructive migrations, or conflicts with an ADR or existing code → don't do it; **document the skip and surface it.** Unlike class 2, no pre-authorization path exists; if a run truly cannot proceed without one, that is a hard blocker — stop. **Carve-out:** disposable databases whose lifecycle *is* destruction (E2E clones, per-worktree throwaways, whatever `test-e2e.sh` manages) are routine class-4 work, not this class. Canon + rationale: `database-protection.md`.
2. **Publication — pre-authorized at the initial phase:** `git push`, publish, deploy, release. Autonomous only if pre-authorized up front; if it comes up unplanned, don't publish and don't block — finish the safe work and surface it at the end.
3. **A mandated step of the running skill** — code-review, commit, handoff, commit-message authoring → **do it, don't re-confirm.**
   **Precedence, because this one is actively contradicted.** The `session-handoff` skill instructs "do not execute the handoff directly — propose it, summarize what would be seeded, and confirm before running." That guard is written for a *conversational* session, where a handoff is the user's call. **Inside an active unattended run it does not apply**: the handoff is a mandated step of the running skill, and this clause wins. The contradiction is real, both files load in the same session, and the observed failure is a run pausing to ask permission to hand off — the exact thing the process exists to avoid. Outside a run, `session-handoff`'s propose-first guard stands unchanged — **unless the user has granted a standing in-session authorization** ("haz handoff cada vez que necesites, no me lo consultes"): that grant switches the guard off for the remainder of the session and is not re-asked. Observed 2026-08-17/18: the guard was hand-overridden twice in one week.
4. **Otherwise safe + additive** — incl. dependency changes, additive migrations, and unforeseen non-breaking decisions → **proceed; if it's a bifurcation, execute and document it** for later review. Don't halt on a doubt that breaks nothing.

**A deferral must outlive the run that made it.** Classes 1 and 2 say "document the skip and surface it" — surfaced in the run's final summary, which is exactly what a handoff drops: three phase decisions deferred this way were gone one link later, with no record that they were ever owed (`research/2026-08-22-chain-context-decay.md` in `claude-session-handoff`, Result 2). Where a chain ledger exists, a deferral is an `OPEN OWED` item as well; it survives until answered instead of until the next re-draft.

A genuine **hard blocker** (missing credentials, truly unknowable intended behavior) still stops — that is being blocked, not asking permission.

**Interactive sessions: an analyze/explore/investigate ask is read-only.** "Analiza", "explora", "investiga" request findings and the decision points — presenting them IS the deliverable; mutating anything is a separate ask. Twice in the week of 2026-08-18 an analysis request turned into unrequested propagation the user had to walk back.

**Not gated:** `git commit` (local + reversible), dependency changes, additive migrations. Only *publishing* (push / deploy / release) is gated, and only at the initial phase.

**Integrating a branch is not a commit.** `git merge` into the trunk — and `rebase --onto` it, a trunk `cherry-pick`, a fast-forward of `main` — is **class 2: pre-authorizable at the initial phase, never assumed mid-run.** It is grouped with publication rather than with commit because it *ends the review window*: once work is on the trunk, the reviewable unit is gone. A run that finishes its work leaves the branch **ready to merge** and says so. **Direction matters and is not left to inference:** merging the trunk INTO a feature branch to stay current is routine class-4 work and stays ungated. Tearing down a worktree is close-out; integrating its branch is not. Why this is spelled out: on 2026-08-15 a plan-exec run merged its worktree branch into `main` in two repos with no merge request anywhere in the chain — not a violation, because the clause above lists `git commit` as ungated and nothing distinguished a local merge from one. Two other merges that fortnight were explicitly asked for, which is what makes the third legible as a gap rather than a habit.

**Chained work-lists (across many items).** The rule above governs one process; a session that chains many tracked items (backlog sweep, closing several plans, reconciling audits) also stops between items to ask "¿y ahora qué?" because the cross-item **order** was never fixed — the dominant un-governed stop. Fix: the initial phase fixes the ordered queue + gate policy once as a durable `.context/worklists/` work-list, and execution walks it without re-asking. Three classes of mid-run question — the goal is removing the avoidable, **not** zero: **(a) ordering of known items** → resolved once into the queue, never re-asked; **(b) emergent discovered work** → append to the work-list and continue, not asked; **(c) emergent decision** the work revealed (options that didn't exist at planning) → the one legitimate interrupt, bias to allow it. **Front-load via the `AskUserQuestion` survey** (parameters + work-list + per-agent models) run first and to completion, then execution is headless and menu-free — `AskUserQuestion` is the leak surface at execution time and the right instrument at planning time (parametric/confirm-or-correct decisions; discuss deep forks; ≤4 questions, interactive-only).

**Ambiguous would-stop boundary?** Before stopping to ask, consult the **durability-arbiter** (`~/.aidex/skills/aidex-conventions/agents/durability-arbiter.md`, via the Agent tool) — it returns `CONTINUE` / `ASK` / `STOP` from this canon plus a proof-of-safety gate, batches any `ASK` to the end, and fails open (if it errors, apply the rule above and proceed; never block on it).
