# Backlog Conventions

Rules for entries in `.context/backlog/`.

> **Read [`00-global.md`](../../aidex-conventions/references/00-global.md) first.** Filename dates, archive, language, cross-references, and minimum front-matter live there. This file only declares what is specific to the backlog (priority taxonomy, `00-index.md` auto-regeneration, body shape).

---

## Location & naming

```
.context/backlog/
├── 00-index.md                     # Auto-regenerated — do NOT hand-edit
├── YYYY-MM-DD-bl-nnn-<slug>.md     # active queue
├── YYYY-MM-DD-bl-nnn-<slug>.md
├── _deferred/                      # open-but-blocked (status: open, blocked_by set)
│   └── YYYY-MM-DD-bl-nnn-<slug>.md
└── _archive/                       # terminal (done / dropped) — closed items
    └── YYYY-MM-DD-bl-nnn-<slug>.md
```

- **Date:** `YYYY-MM-DD` per D-01 (creation date, not the date work starts).
- **Id segment:** the item's `id` lowercased (`bl-027`), between the date and the slug.
  Date-first keeps D-01's chronological sort; a fixed position right after it puts the
  code in the same column on every line, which a trailing suffix does not.
  Items predating this convention keep `YYYY-MM-DD-<slug>.md` — both forms satisfy
  `validate.py`'s `ISO_FILENAME`, and nothing resolves an item by parsing its filename.
- **Slug:** kebab-case, 3–6 words max. Describes *what*, not status.
- **Deferred:** `_deferred/` holds open items the team intends to do but cannot start
  (external blocker). `status` stays `open`, `blocked_by` MUST be populated, and they
  are **not** counted in the active queue. NOT the same as `_archive/`. See
  [The deferred layer](#the-deferred-layer-_deferred).
- **Archive:** required (D-05, amended by D-10); move `done` / `dropped` entries to `_archive/` **on close** — immediately, not after a delay. `close-item.sh` does this atomically.

## `00-index.md` (auto-regenerated)

The backlog index is **generated by `aidex-backlog` from front-matter** — never hand-edit it. Running `aidex-backlog --reindex` (or any `aidex-backlog` write) regenerates it.

The generated index groups entries by `priority`, lists blocked items in a separate section, and shows status counts:

```markdown
# Backlog

_Auto-generated by `aidex-backlog` from front-matter. Do not edit by hand._

**Updated:** 2026-05-14
**Active:** 12 · **Blocked:** 3 · **Doing:** 2

## P0 — Critical

- **BL-042** · **[Fix data loss in export](2026-05-13-fix-data-loss-export.md)** — open · M
- …

## P1 — High

- …

## P2 — Medium

- …

## P3 — Low

- …

## Blocked

- **BL-051** · **[Waiting on vendor X](2026-04-22-waiting-on-vendor-x.md)** — open · P1 · blocked_by: "vendor support ticket"

## Deferred

- **BL-018** · [Migrate to vendor v2 API](_deferred/2026-04-22-migrate-vendor-v2.md) — P1 · blocked_by: "vendor v2 GA" · 2026-04-22

---

_Archived items: see [`_archive/`](_archive/)._
```

> **`## Blocked` vs `## Deferred`.** `## Blocked` lists items still in the active
> queue (root of `backlog/`) that happen to carry a `blocked_by` modifier. `##
> Deferred` lists items physically moved out to `_deferred/` — parked indefinitely,
> off the active queue. Use `defer` to move an item from Blocked-in-queue to Deferred.

## Front-matter (required)

```yaml
---
title: "Export dashboard as CSV"
id: BL-042
status: open
created: 2026-04-15
updated: 2026-04-15
origin: audit
origin_ref: audit/ux/2026-04-15-ux-review/IDEA-FF-2
priority: P2
type: task
estimate: M
blocked_by: ""
escalated_to: ""
commits: ""
---
```

This is the **complete 13-field schema `register-item.sh` writes** — the single source
for the entry front-matter. `title`, `status`, `created`, `updated` are the required
global fields from [`00-global.md` §7](../../aidex-conventions/references/00-global.md#7-front-matter-minimum-d-07);
the rest are backlog-specific. When hand-authoring an entry, write all 13 — `id` and
`commits` are **machine-required** (the lifecycle breaks without them), while
`origin_ref` and `estimate` are human-optional (no script branches on them).

| Field | Values / format | Notes |
|---|---|---|
| `title` | quoted string | Global (§7). |
| `id` | `BL-NNN` | **Machine-required (D-09):** `close-item.sh` resolves the target by `id` (dies with "no active backlog item with id" otherwise); `harvest-commit.sh` matches on it. `register-item.sh` assigns it, and the filename carries it. Must match `^BL-[0-9]{3}$` — `--reindex` fails on a duplicate **or** a nonconforming id. `next_backlog_id` counts only conforming ids toward the max, so a hand-authored `BL-20260610` no longer inflates the sequence; it is still reported until fixed. |
| `status` | `open` · `doing` · `done` · `dropped` | Base lifecycle from [`00-global.md` §6](../../aidex-conventions/references/00-global.md#6-status-vocabulary). |
| `created` · `updated` | ISO `YYYY-MM-DD` | Global (§7). |
| `origin` | `manual` · `audit` · `issue` · `request` | Where it came from. (A cross-repo counterpart from `--escalate-to` carries `origin: <source-repo>/<id>` — see [Cross-project routing](#cross-project-routing-the-bl-035-handshake).) |
| `origin_ref` | `<type>/<filename>` (D-03) or empty | *Human-optional:* provenance archaeology — no script reads it. Format depends on origin — see below. |
| `priority` | `P0` · `P1` · `P2` · `P3` | Code, never free text. See [Priority taxonomy](#priority-taxonomy). |
| `type` | `bug` · `improvement` · `task` · `idea` | **Work-kind facet, one queue** (ADR 2026-07-23). Closed and small by design; the index groups by priority, not type — type renders as a chip. Default `task`. Absent is a warn-then-ratchet nudge (existing items are not retro-fixed); a value outside the enum is a violation. `_deferred` is a **state**, not a type. |
| `estimate` | `XS` · `S` · `M` · `L` · `XL` | *Human-optional:* T-shirt sizing, display-only (index one-liner + dash cell); no logic branches on it. Independent of priority. |
| `blocked_by` | Free text or `<type>/<filename>` | Non-empty means parked waiting on third party; priority stays. |
| `escalated_to` | `<type>/<filename>` (D-03) or empty | Set when work moves to a plan (typically combined with `status: doing`). A cross-repo escalation carries `<target-repo>/<id>` — see [Cross-project routing](#cross-project-routing-the-bl-035-handshake). |
| `commits` | space-separated SHAs, or empty | **Machine-required (D-09):** `harvest-commit.sh` appends resolved SHAs here so closure is verifiable, not just asserted. |

### `origin_ref` formats

| Origin | Format | Example |
|---|---|---|
| `manual` | empty | — |
| `audit` | `audit/<methodology>/<run>/<finding-id>` | `audit/ux/2026-04-15-ux-review/IDEA-FF-2` |
| `issue` | `issue/<id>` | `issue/ISSUE-042` |
| `request` | `request/<filename>` | `request/2026-04-10-export-feature.md` |

## Priority taxonomy

The `priority` field is a **code**, never free text. Four levels plus a `blocked_by` modifier.

| Level | Label | Criteria | Target time |
|---|---|---|---|
| **P0** | Critical | Production bug breaking operations · active security breach · CI blocked · data loss | This week |
| **P1** | High | Blocking feature for a flow · data quality/correctness · severe regression · external commitment | Next 2 weeks |
| **P2** | Medium | Important non-blocking improvement · scoped tech debt · significant UX issue | Next release |
| **P3** | Low | Nice-to-have · cosmetic refactor · pull-driven | No date |

**Blocked modifier:** when an item waits on a third party, keep its `priority` (do NOT downgrade) and set `blocked_by`. The auto-generated index surfaces it under "Blocked".

Re-evaluate priorities every two weeks. If you want `P1.5`, pick one — the taxonomy is intentionally coarse.

### Legacy mapping

| Legacy value | → | New code |
|---|---|---|
| `Critical`, `Urgent`, `URGENT` | → | `P0` |
| `High`, `high` | → | `P1` |
| `Medium`, `medium`, `Planned` | → | `P2` |
| `Low`, `low` | → | `P3` |

## Body structure

```markdown
# <title>

## Context

<2–5 sentences: why this is worth doing, what's the value, what's the alternative>

## Acceptance

Done means:

- <concrete, verifiable criterion>
- <another one>

## Notes

<optional: links to related findings, plans, discussions>
```

**Acceptance** is optional at registration (a parked idea can defer it) and required at
`open → doing` promotion — an entry you are about to start must state what done means.
Write criteria as plain `Done means:` bullets, **not** `- [ ]` checkboxes: measured across
250 entries, 88% of closed items were archived with zero boxes ever checked, so the checkbox
implied a tracking contract nothing honored.

Keep entries short. If it needs more than one screen of content, it belongs in a plan.

## Lifecycle

```
open ⇄ _deferred (blocked) ──▶ doing ──▶ done
  │                              │
  └──────────────────────────────┴────▶ dropped
```

### open ⇄ _deferred (blocked)

See [The deferred layer](#the-deferred-layer-_deferred). Deferring is **reversible**
(open ⇄ `_deferred/`); it is not a close. Use the `defer` / `reactivate` sub-actions.

### open → doing

Typically when someone starts work. Update `status: doing`, bump `updated`. If a plan exists, set `escalated_to: plan/<filename>` and add a link in Notes.

### doing → done

Entry represents completed work. Per D-10, archive to `_archive/` **on close** — immediately, not after a delay (use the `close` sub-action, which does it atomically).

### * → dropped

Set `status: dropped` and document the reason in Notes:

```markdown
- **Dropped 2026-04-20:** duplicate of `2026-04-15-export-csv.md` (merged there).
```

## The deferred layer (`_deferred/`)

`backlog/_deferred/` is for items the team **intends to do but cannot start** because
of an external blocker (a third-party dependency, an upstream decision, a release
gate). It is the "open but parked indefinitely" layer.

**Invariants:**

- `status` stays `open` — deferring is **not** a close. Closed items go to `_archive/`.
- `blocked_by` MUST be populated (the reason it's parked). An item in `_deferred/`
  with an empty `blocked_by` is a convention violation.
- Deferred items are **not** counted in the active queue (the P0–P3 sections) and
  are listed separately under `## Deferred` in `00-index.md`.
- `_deferred/` is distinct from `_archive/`: archive is **terminal** (`done` /
  `dropped`); deferred is **reversible** (a held-open item).

**Deferring (`defer`):** moves the file from the active root to `_deferred/`,
sets/appends `blocked_by`, stamps `updated`, and regenerates the index.

```bash
bash scripts/defer-item.sh defer BL-018 --reason "vendor v2 API not yet GA"
# or by slug:
bash scripts/defer-item.sh defer migrate-vendor-v2 --reason "vendor v2 API not yet GA"
```

**Reactivating (`reactivate`):** moves the file back to the active root, clears
`blocked_by`, stamps `updated`, and regenerates the index.

```bash
bash scripts/defer-item.sh reactivate BL-018
```

Always use the `defer` / `reactivate` sub-actions — never move the file or edit
`blocked_by` by hand (the index regen and `updated` stamp would drift).

## Promoting to a plan

When a backlog entry grows beyond one-screen scope:

1. Create `.context/plans/YYYY-MM-DD-<slug>/` with phases.
2. Update the backlog entry: `status: doing`, `escalated_to: plan/YYYY-MM-DD-<slug>`. Add a Notes line linking the plan.
3. Keep the backlog entry — it becomes the "why" while the plan becomes the "how".
4. When the plan completes, update the backlog entry to `status: done`.

Don't delete the backlog entry — it's the origin trail.

## Cross-project routing (the BL-035 handshake)

An item discovered in project A whose work belongs in project B (a shared boilerplate,
a global skill, `aidex` itself) must not sit stranded where nobody who can act on it
will see it. `register-item.sh --escalate-to <target-repo-path>` registers a **linked
pair**:

- the **source** repo carries `escalated_to: <target-repo>/BL-NNN` (points at where the
  work now lives);
- the **target** repo carries `origin: <source-repo>/BL-MMM` (records where it was
  discovered);
- both indexes are regenerated.

```bash
# Discovering a new cross-repo item (registers a fresh source stub + counterpart):
bash scripts/register-item.sh --escalate-to /path/to/boilerplate \
  --title "Host shared X in the boilerplate" --priority P2 --type improvement

# Routing an item that already exists (stamp it instead of duplicating):
bash scripts/register-item.sh --escalate-to /path/to/aidex \
  --source-id BL-172 --title "…"
```

> **Known gap (owned by the cross-ref-schema package, echo BL-206).** A cross-repo
> `escalated_to: <target-repo>/BL-NNN` uses a repo prefix, not an artifact-type prefix,
> so `validate.py`'s `<type>/<filename>` cross-ref check flags it as
> `cross-ref-format-invalid` if you run the validator in the source repo. The counterpart's
> `origin` is validate-clean (`origin` is not a cross-ref field). Widening the cross-ref
> grammar to accept repo-qualified refs is deferred to that package — do not special-case
> it here.

## When NOT to create a backlog entry

- **Work starting this session:** just do it; no entry needed.
- **No acceptance criteria:** that's an idea, not a backlog item. Capture as an audit `opportunity` first.
- **One-line bug fixes** you're doing right now: commit it, reference the finding in the commit message.
- **Stakeholder asks:** go to `.context/requests/` first; become backlog only on acceptance.

---

## Anti-patterns

- **Duplicate entries** — search first (`grep -r "similar title" .context/backlog/`).
- **Entry without `origin`** — always fill, even if `manual`.
- **Changing priority without updating `updated`** — keeps the sort order honest.
- **Hand-editing `00-index.md`** — your edit will be erased on the next `aidex-backlog --reindex`.
- **Leaving `done` entries in the active root** — archive on close (D-10), not after a delay; run `sweep.sh` if any linger.
